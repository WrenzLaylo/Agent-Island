# v0.4.3 — The agent's own choices, all of them

Two related changes to how permission prompts are presented. Both come from the
same principle: the terminal is authoritative about what it offered, and the
island's job is to relay that faithfully, not to summarise it.

## The island showed its own wording

Claude prints:

```
1. Yes
2. Yes, and don't ask again for: curl *
3. No
```

The island rendered "Allow once", "Don't ask again", "Deny". The middle row is
why this mattered — the terminal states the *scope* of the standing permission,
and the paraphrase dropped it, so a narrow grant and a dangerously broad one
read identically in the pill.

All three adapters already captured `{ index, key, label }` and discarded the
label before it left the main process. It is now carried through as
`choiceOptions` and rendered verbatim.

## The island showed fewer choices than the terminal offered

The more serious half. Rendering was driven by the *classified* decisions, and
classification silently lost two kinds of option:

- anything the classifier did not recognise — `Yes, but let me edit the command
  first` maps to none of `once`/`session`/`always`/`deny`
- any second option landing on a slot already taken, because `responseKeys`
  deduplicates by key

Measured against a real four-option panel:

```
Terminal offered:   1. Yes
                    2. Yes, but let me edit the command first
                    3. Yes, and don't ask again for: npm *
                    4. No

Island rendered:    1. Yes
                    3. Yes, and don't ask again for: npm *
                    4. No
```

Option 2 was not disabled or marked unavailable — it was absent, with nothing
to indicate a choice was missing. The one the user wanted might be the one that
vanished.

`approvalRows()` now builds from the raw option list, attaching a
classification by index where one exists. Classification is advisory: it
decides only which row needs the permanent-access confirmation, and which rows
sit behind the approve-safety gate. It never decides what is displayed.

Answers are sent as `optionIndex` — the agent's own digit — so an unclassified
option is as answerable as any other. An option with no classification is gated
as an approval, never as a denial: treating a row as harmless because the
classifier failed to recognise it would be exactly the wrong default.

## What is unchanged

The permanent-access confirmation still fires, and denial stays clickable when
a request is no longer safe to approve. The invented labels remain as a
fallback for requests carrying no captured wording — the Hermes IPC bridge, and
any wrapper older than this build — because mixing two vocabularies in one list
would be worse than either alone.

## Verification

120 unit tests (was 116), both tsconfigs clean, build clean. Eleven cover
`approvalRows` and `isDenyRow`: wording preserved including grant scope, an
unrecognised option rendered, that option left unclassified rather than guessed,
ordering by agent numbering, the empty fallback, options with no classifications
at all, no mutation, and an unclassified row treated as an approval.

Live-verified against an isolated registry, reading back what reached the
wrapper's inbox:

- the four-option panel renders **all four** rows with their digits
- clicking the previously-dropped option 2 wrote `{ "optionIndex": 2 }`
- clicking the permanent option raised the confirmation and wrote **nothing**
  until it was confirmed
- confirming wrote `{ "optionIndex": 3 }` — the path left unverified in v0.4.2

Not verified: a real Claude session end to end; multi-monitor handoff; Codex
and Hermes against real installs.
